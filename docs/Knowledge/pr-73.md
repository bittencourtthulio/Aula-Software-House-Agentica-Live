# Triagem de toda issue e consulta rápida ao PO antes de desenvolvimento

## Quando consultar
Dúvida que abre PR desnecessária, issue manual sem atendimento, CLI com texto
antes do JSON ou atendimento bloqueado que precisa retomar.

## Contexto e causa
A investigação da issue #72 comprovou falha de parse do stdout inteiro.
O código também exigia origin:app, classificava dúvidas comerciais como code
e o cron só concluía respostas já publicadas. O histórico de issue-9/pr-10
mostrava que uma orientação já havia passado por PR sem alteração de produto.
IDs consultados: issue-9, pr-10 e pr-12; comportamento atual conferido no código.

## Solução e decisão
Proposta da PR #73: toda issue normal entra na triagem, mantendo exclusão de PRs
e tarefas antigas de curadoria. N1 acolhe e propõe; coordenador confirma solução
sem desenvolvimento, pede esclarecimento, solicita consulta ao PO ou encaminha
code. Consulta ao PO retorna ao N1 e coordenador sem criar PR; só code solicita
atribuição ao coding agent. A classificação exige evidências, não palavras-chave.

Leitura do CLI aceita um único objeto completo com introdução/cercas, valida
requestId/outcome/texto/evidências e rejeita ambiguidade. Uma nova chamada pode
corrigir retorno inválido. Issues manuais têm requestId derivado de repo/número.
Respostas e esclarecimentos usam revisão do pedido e comentários humanos para
não reutilizar uma orientação anterior após nova pergunta.

O cron retoma issues abertas sem atribuição, registra bloqueios, continua o
lote após falha individual e limita tentativas automáticas por revisão a três,
com espera de 5 e 15 minutos. Esclarecimento aguarda cliente; tentativa manual
ou nova mensagem/edição permite reanálise. Resposta publicada retoma só fechamento.

## Evidências e validação
Em 11/11/2026, na branch da proposta, npm test concluiu 59 testes aprovados
(com permissão para abrir servidores HTTP locais), npm run build passou e
git diff --check não encontrou erros. Testes de regressão cobrem introdução e
cercas, contrato parcial/ambíguo, reformatação, PO, decisão de code, issues sem
label/requestId, sincronização de texto ao ticket, intervalo/limite de retomada,
falha individual no lote, espera por cliente e nova pergunta após resposta.
Os testes usam substitutos das APIs e do CLI; não invocaram IA remota.

## Limites e prevenção
PR aberta é proposta; ainda não há integração confirmada nem entrega comprovada
no atendimento #72. Não fechar a issue só por integrar o controlador.
Tokens/licença Copilot e cron continuam necessários. Três falhas exigem retomada
manual ou novo contexto humano. Se o GitHub não aceitar comentários, só o log
pode relatar o bloqueio. Falhas não são convertidas em necessidade de código.
O runtime mantém ferramentas somente de leitura e não expõe stdout/stderr nas
mensagens. Não há promessa de resposta em segundos, deploy ou merge automático.
